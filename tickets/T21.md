# T21 — Child dashboard UI

## Context
Spec §3.6: "Child sees their own remaining time, buckets, and schedules (transparency reduces
circumvention). Child can request: extra time, unblock a site/app, schedule change." Spec §5:
"Child dashboard shows: time left today, current session remaining, next break length — full
transparency." Spec §6: the "Still watching?" 30-second prompt (Level 0 presence check) is
child-facing UI.

This screen is the RN-side consumer of T03's `BucketEngine`, T04's `evaluatePresence`, and
T05's schedule engine — driven locally on-device for offline-capable enforcement (spec §7:
"offline-first enforcement... all blocking and bucket logic runs locally"). Since there's no
real Android foreground-service/native timer in this environment yet (that arrives in T24), this
ticket wires the **pure engines** (already fully built and tested in T03–T05) into a
JS-side ticking clock (`setInterval`) as the cross-platform baseline — the native module
(T24) will later replace/augment the timer source with real OS-level enforcement, but the UI
and engine-calling logic built here must be correct and testable independent of that.

## Caller contract for `BucketEngine.endSession` (orchestrator-resolved, see LEDGER.md T03 entry)
`endSession` folds elapsed time into daily usage AND opens a `BreakState` that makes the next
`startSession` refuse until the full `mandatoryBreakMinutes` has elapsed. Per spec §5 ("a break
shorter than the mandatory break duration does not reset the session clock"), **only call
`endSession` when `tick()` reports `mustEnd: true`** (session cap genuinely reached), or when a
pause has been affirmatively classified elsewhere as a qualifying break (e.g., a presence
trigger, T04, judged the child absent for longer than the break threshold). **Never call
`endSession` for a trivial pause** (app backgrounded briefly, screen momentarily off, a
"Still Watching?" prompt answered promptly) — for those, simply keep ticking the same
`SessionState`; `tick()`'s elapsed-since-`startedAt` calculation already does not reset on its
own, so no special handling is needed as long as `endSession` isn't called prematurely.

## Requirements
In `app/src/child/dashboard/`:

1. `ChildDashboardScreen.tsx` — shows: time left today (from `DailyUsageState` /
   `ScreenTimePolicy`), current session remaining (from `SessionState` via `BucketEngine.tick`),
   next break length, and the active schedule window (from T05's engine) in plain language
   ("Bedtime starts at 9:00 PM"). Ticks every second via `BucketEngine.tick`, firing 5-min/1-min
   warning banners and a "wrap up" prompt per T03.
2. `StillWatchingPrompt.tsx` — modal shown when Level-0 presence logic (T04) needs a response;
   30-second countdown; tapping "Yes" resets the idle clock, timing out feeds
   `stillPromptTimedOut: true` into `evaluatePresence` on the next tick.
3. `RequestScreen.tsx` — child-side form to create a `ChildRequest` (extra_time/unblock/
   schedule_change) via T19's `POST /requests` endpoint, with a pending-requests list showing
   status.
4. `useLocalBucketEngine(policy, initialUsage)` hook wrapping T03's `BucketEngine` +
   T05's `isWithinAllowedWindow` + T04's `evaluatePresence`, exposing the ticking state to the
   screens above; on presence-trigger, calls `BucketEngine.refundMinutes` locally and posts the
   `DeviceEvent` to `event-ingest` (T09) when connectivity allows (queue-and-retry if offline —
   simple in-memory queue is sufficient for this pass, do not over-build a full offline sync
   engine here since spec's fuller multi-device reconciliation lives in T03's
   `reconcileOffline`, already built).
5. Tests: dashboard reflects a fixture policy/usage state correctly; 5-min/1-min warnings fire
   at the right tick; Still-Watching timeout triggers a presence pause+refund end-to-end through
   the hook (this is the one integration test worth writing across T03+T04+T05+this ticket —
   write it); request creation round-trips to a pending item.

## Out of scope
- Native-level enforcement (actually locking the OS screen, real accelerometer/camera signals)
  — T22-T25. This ticket's timer is a correct, tested, offline-capable JS-side baseline that
  those native tickets plug real signals into.
- Parent-side approve UI — already built, T19.
