# T19 — Child request / parent approve flow

## Context
Spec §3.6: "Child can request: extra time, unblock a site/app, schedule change. Parent
approves/denies from a push notification." Reuses `ChildRequest`/`RequestType`/`RequestStatus`
(T02).

## Requirements
Backend (`packages/backend/`):
1. `requests/index.ts` edge function: `POST /requests` (child creates a `ChildRequest`,
   dispatches a push to parent devices via T08's `PushDispatcher` — real-time, matching the
   spec's "approves/denies from a push notification" framing), `POST /requests/:id/resolve`
   body `{ approve: boolean }` — sets `status`, `resolvedAt`; if `approve && type ===
   'extra_time'`, calls `BucketEngine`-adjacent logic to grant the requested minutes (add a
   pure helper `applyApprovedExtraTime(dailyUsage, categoryId, minutes): DailyUsageState` in
   `packages/domain/src/buckets/engine.ts` from T03 — a small addition to that file, call it
   out explicitly as touching a prior ticket's file); if `approve && type === 'unblock'`,
   updates the relevant `ContentFilterPolicy`/`AppRulePolicy` list; if `approve && type ===
   'schedule_change'`, updates `SchedulePolicy[]` per the request payload.
2. Tests: request creation dispatches push; approve on each of the 3 request types produces
   the correct policy/usage mutation; deny leaves policy/usage untouched.

Frontend (`app/src/parent/requests/`):
1. `RequestsInboxScreen.tsx` — pending `ChildRequest` list, approve/deny buttons calling the
   resolve endpoint, resolved history below.
2. Tests: approve/deny call the correct endpoint+body; resolved items move out of the pending
   section.

## Out of scope
- Child-side request-creation UI — T21.
- Push tap-through deep-linking straight to this screen — nice-to-have, not required by spec
  text ("from a push notification" is satisfied by the push existing and this screen being
  reachable; deep-link wiring noted as a follow-up if not reached).

## Done when
- [ ] `npm test -w packages/backend` and `npm test -w app` pass new tests (paste output).
- [ ] All 3 request types verified (via test) to produce the correct mutation on approval.
- [ ] The `applyApprovedExtraTime` addition to T03's file is called out explicitly in the report.
