# T03 — Usage Buckets engine

## Context
Differentiator 2 from the spec (§5) — the core selling point of the product and the single
most important piece of pure logic in the whole system. This is fully unit-testable with no
external dependencies, so it must be built to production quality with thorough tests — no
hand-waving here, this is the part we can 100% verify in this environment.

Restated from spec §5, verbatim rules this engine must implement:
- **Total daily time** (e.g. 4h/day): resets at a parent-set time, default midnight.
- **Max session length** (e.g. 45 min): continuous-use cap; at the cap the session ends
  (device/app locks).
- **Mandatory break** (e.g. 15 min): minimum lock-out after a session ends before a new session
  can start. A break *shorter* than the mandatory duration does **not** reset the session
  clock — i.e. resuming early continues accruing against the *same* session, it does not grant
  a fresh full session.
- **Session count** (optional, e.g. max 5 sessions/day): caps number of distinct sessions.
- 5-minute and 1-minute warnings before session end.
- **Grace finish** (optional, parent toggle): +3 minutes once per session, consumable once.
- Buckets differ by category (`BucketPolicy.perCategory` from T02, falling back to `.default`).
- Buckets compose with schedules: a session must not be allowed to cross into a window where
  the category isn't in `SchedulePolicy.allowedCategories` (schedule engine is T05 — for this
  ticket, accept an injected `isWithinAllowedWindow(categoryId, atTime): boolean` function; do
  not implement schedule logic here, just call the injected predicate).
- Multi-device: state must be representable as a plain serializable snapshot so it can sync via
  backend and reconcile after offline periods, conservatively (i.e. on reconnect, if two
  devices both report usage for overlapping time, treat as sequential/additive, never double-
  subtract remaining time below zero, never grant time back beyond what was actually used).

## Requirements
In `packages/domain/src/buckets/`:

1. `types.ts` — `SessionState` (`categoryId`, `startedAt`, `elapsedMinutes`, `graceUsed: boolean`,
   `warnings5MinFired: boolean`, `warnings1MinFired: boolean`), `BreakState` (`categoryId`,
   `startedAt`, `requiredMinutes`), `DailyUsageState` (`date`, `perCategoryMinutesUsed:
   Record<string, number>`, `perCategorySessionCount: Record<string, number>`,
   `totalMinutesUsed: number`).
2. `engine.ts` — a pure `BucketEngine` class or function set, given `BucketPolicy` +
   `ScreenTimePolicy` (for the daily/weekly totals) + current `DailyUsageState` +
   `SessionState | null` + `BreakState | null`, exposing:
   - `startSession(categoryId, now, isWithinAllowedWindow): Result` — refuses (returns a
     typed refusal reason) if: daily/weekly total already exhausted, session count cap hit,
     an active mandatory break hasn't elapsed, or the schedule predicate returns false.
   - `tick(now): TickResult` — advances elapsed time, returns whether to fire the 5-min/1-min
     warning, whether the session must end (cap reached), and remaining minutes.
   - `requestGraceFinish(now): Result` — grants +3 min if `graceFinishEnabled` and not already
     used this session; otherwise refused.
   - `endSession(now): { updatedDailyUsage, break: BreakState }` — computes whether the
     just-ended break-then-resume pattern qualifies as "new session" per the mandatory-break
     rule above.
   - `refundMinutes(categoryId, minutes, now)` — decrements `totalMinutesUsed` /
     `perCategoryMinutesUsed` (floored at 0) for the presence-detection refund feature (spec §6);
     used by T04.
   - `reconcileOffline(localSnapshot, remoteSnapshot): DailyUsageState` — merges two
     `DailyUsageState`s for the same child/date conservatively per the multi-device rule above
     (sum usage, never let merged total exceed the greater of the two `totalMinutesUsed` plus
     any genuinely non-overlapping intervals — implement via additive merge of
     `perCategoryMinutesUsed` capped by `ScreenTimePolicy.dailyLimitMinutes`, documented inline
     with a comment on the chosen conservative strategy since this is a genuine design choice).
3. `__tests__/engine.test.ts` — cover, at minimum, one test per rule listed in Context above,
   including: short break does not reset session; grace finish usable once only; category
   override vs default; session count cap; offline reconcile does not double-count and does not
   exceed the daily cap.

## Review findings (address before DONE)

A reviewer found that `reconcileOffline` (`engine.ts`) breaks its own data invariant with 2+
categories. Every other method keeps `sum(perCategoryMinutesUsed) === totalMinutesUsed`, but
`reconcileOffline` caps `totalMinutesUsed` and each `perCategoryMinutesUsed[c]`
**independently** against `dailyLimitMinutes` instead of deriving the per-category values from
the same clamp applied to the total. Reproduced case: two snapshots each
`{ totalMinutesUsed: 200, perCategoryMinutesUsed: { games: 100, education: 100 } }`,
`dailyLimit: 240` → merges to `{ totalMinutesUsed: 240, perCategoryMinutesUsed: { games: 200,
education: 200 } }` — sum of per-category (400) vastly exceeds the reported total (240). This
matters because `ScreenTimePolicy.perCategory` (a per-category daily cap, already in T02's
types) will eventually be enforced against these numbers, and an inflated/inconsistent
post-reconcile per-category figure could cause wrong refusals or refunds.

**Fix required:** make the merge internally consistent. Recommended approach: compute the
additive per-category sums and additive total first (uncapped), then if the additive total
exceeds `dailyLimitMinutes`, scale every category's summed minutes down by the same factor
(`dailyLimitMinutes / additiveTotal`) so `sum(perCategoryMinutesUsed) === totalMinutesUsed`
holds after clamping, rather than clamping each field independently. Update the docstring to
state the invariant explicitly. Add a regression test with **2+ categories** exercising this
exact case (the current test suite only ever uses one category, `GAMES`, for reconcile tests —
add coverage for the multi-category case as the ticket's own done-when already required
"offline reconcile does not double-count," which wasn't actually exercised for >1 category).
