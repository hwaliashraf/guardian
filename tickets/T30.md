# T30 — Integration verification

## Context
This is the final ticket. Its job is to verify the **deliverable against the ORIGINAL spec**
(`../project_spec_parental_app.md`), not against the tickets (decomposition can drift from
intent over 29 tickets) — and to check the seams where tickets' work meets: does T21's child
dashboard actually call T03/T04/T05's engines with the signatures those tickets shipped? Does
T08's policy-sync actually enforce T06's gating the way T14/T16/T17/T20's UI assumes? Does
T22's Kotlin VPN's DNS-decision logic actually match the ported `dnsDecision.ts` it was supposed
to mirror?

Read `../LEDGER.md` in full first — it has every Phase-0 scope decision and every risk/patch
noted along the way; use it to know what "done" is supposed to mean for this pass (whole-shebang
code, native modules unverified-by-environment-necessity but real, everything else genuinely
verified with evidence).

## Requirements
1. **Full test suite, root**: `npm install && npm run lint && npm run typecheck && npm test
   --workspaces --if-present` — paste complete output. Any failure here is a blocking finding,
   not a note.
2. **Spec traceability pass**: go through `project_spec_parental_app.md` section by section
   (§3.1 through §3.8, §4, §5, §6) and for each bullet point, name the file(s) implementing it
   and its verification status (tested-and-passing / written-but-environment-unverified /
   not-built). Produce this as `docs/spec-traceability.md` — this is the single most important
   artifact of this ticket; a gap here is a decomposition failure the orchestrator needs to
   know about, not something to paper over.
3. **Seam checks** (exercise these concretely, don't just read the code):
   - Instantiate T03's `BucketEngine` with a policy built through T13/T14's UI's expected shape
     and confirm a full session lifecycle (start → tick → warnings → grace → end → break →
     mandatory-break-blocks-early-restart) works end to end in one integration test
     (`packages/domain/src/__tests__/integration.fullLifecycle.test.ts` if it doesn't already
     exist from T21).
   - Confirm T06's `TIER_FEATURES` gating is actually enforced by T08's policy-sync AND
     reflected identically in T14/T16/T17/T20's UI upsell conditions (grep for
     `hasFeature`/`assertFeature` call sites and confirm every gated feature named in spec §3.8
     has both a backend and a UI gate, not just one).
   - Confirm the `youtube_view` payload contract (T18 documented it, T23 was supposed to
     produce it) matches exactly — diff the two ticket files' payload shape descriptions if
     needed.
   - Confirm every `RISK:`/limitation note left by T23, T24, T25, T27 was actually addressed
     (either fixed in a later ticket, or explicitly still open) — list each one's current
     status.
4. **Environment/verification honesty audit**: grep every ticket's executor report (if
   available in LEDGER.md's ticket log) for "UNVERIFIED"/"BLOCKED" claims and cross-check that
   `SETUP.md` actually has a corresponding actionable section for each. Flag any unverified
   claim that has no corresponding SETUP.md entry — that's a process gap.
5. **Final SETUP.md pass**: confirm it now reads as a complete, ordered runbook a human could
   follow start-to-finish to go from this repo to a running app on a real Android device and
   a partially-working iOS build (DNS profile + content blocker, pending the FamilyControls
   entitlement).

## Out of scope

  it (BLOCKED/ESCALATE per the orchestrator's protocol) rather than silently patch unrelated
  tickets' work; small doc/SETUP.md corrections are fine to make directly.
