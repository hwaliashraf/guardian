# T07 — Supabase schema, migrations & RLS

## Context
Backend choice (Phase-0/LEDGER.md decision): **Supabase** (Postgres), developed and verified
**locally** via the Supabase CLI + Docker — no cloud account exists or is required for this
pass. Environment note from LEDGER.md: Docker is installed (`docker -v` succeeds) but the
daemon was not running when last checked. **Try starting it yourself first**
(`open -a Docker` on macOS, then poll `docker ps` every few seconds up to ~90s) since this is
just launching an already-installed local app, not a new install — if it still isn't reachable
after that, proceed to write all schema/migration files for real, but report verification as
BLOCKED-by-environment and add exact manual steps ("open Docker Desktop, then run
`supabase start`") to `SETUP.md`'s "Docker" section.

Data model (from `packages/domain/src/types.ts`, T02 — restated in full, this ticket's tables
must map 1:1 to these fields, using `snake_case` column names per Postgres convention):

```
Family { id, name, createdAt }
Parent { id, familyId, email }
Child { id, familyId, name, birthdate }
Device { id, childId, platform('android'|'ios'), name, registeredAt }
Subscription { familyId, tier('free'|'standard'|'premium'), deviceLimit }
Policy { id, childId, version, screenTime(jsonb), buckets(jsonb), schedules(jsonb),
         vacation(jsonb), contentFilter(jsonb), appRules(jsonb), presence(jsonb),
         tamper(jsonb), instantPause(bool) }
DeviceEvent { id, deviceId, childId, type, payload(jsonb), occurredAt }
ChildRequest { id, childId, type, payload(jsonb), status, createdAt, resolvedAt }
```

## Requirements
In `packages/backend/supabase/` (Supabase CLI project layout):

1. Run `supabase init` (or hand-author the equivalent `config.toml` if the CLI isn't
   installed/available — install via `brew install supabase/tap/supabase` first, that's a
   reasonable local dev-tool install, not a system-wide risky change; note in SETUP.md if it
   can't be installed).
2. `supabase/migrations/0001_init.sql` — creates all 7 tables above with:
   - UUID primary keys (`gen_random_uuid()` via `pgcrypto`), `NOT NULL` on required fields,
     foreign keys (`Parent.familyId -> Family.id`, `Child.familyId -> Family.id`,
     `Device.childId -> Child.id`, `Policy.childId -> Child.id`, etc.), `ON DELETE CASCADE`
     for family/child-scoped rows.
   - `CHECK` constraints for enum-like columns (`platform IN ('android','ios')`, `tier IN
     ('free','standard','premium')`, `status IN ('pending','approved','denied')`).
   - Sensible indexes: `device_event(child_id, occurred_at)`, `policy(child_id, version)`
     unique, `child_request(child_id, status)`.
3. `supabase/migrations/0002_rls.sql` — enable RLS on every table; policies such that:
   - A parent (`auth.uid()` matches a row in `Parent` for that family) can `SELECT`/`INSERT`/
     `UPDATE` everything scoped to their own `family_id` (via a join/subquery), never another
     family's rows.
   - A child device (service-role or a scoped device JWT — model as a `device_id` claim) can
     `SELECT` its own child's active `Policy`, `INSERT` its own `DeviceEvent`s and
     `ChildRequest`s, but **cannot** write `Policy` or read another child's/family's data.
   - Document the auth model assumption clearly in a comment block at the top of the file
     (this is a design decision an executor is allowed to make, since the spec doesn't specify
     Supabase Auth internals — flag it for human review in the report as a `RISK:` note, not
     silently).
4. `packages/backend/package.json` (workspace member) with a `test` script.
5. Attempt local verification: `supabase start` then `supabase db reset` (applies all
   migrations) then a smoke-test script `packages/backend/scripts/smoke.ts` that, using
   `@supabase/supabase-js` (add as a dependency) against the local instance, inserts a Family →
   Parent → Child → Device → Policy → DeviceEvent → ChildRequest chain and reads them back,
   asserting the RLS-bypassing service-role key can do so (this is the local/dev smoke test,
   not an RLS-as-a-parent-vs-parent test — that's covered by pgTAP tests below if time
   permits, otherwise note as a follow-up).
6. If `supabase start` succeeds: run the smoke script for real and paste its output as evidence.
   If it does not (Docker unreachable even after the retry above): still write items 1-5 for
   real, and in the report state plainly "migrations and RLS policies are written but UNVERIFIED
   — could not start local Supabase (Docker daemon unreachable)"; add the exact commands
   (`supabase start`, `supabase db reset`, `npx tsx packages/backend/scripts/smoke.ts`) to
   `SETUP.md` under "Docker" / "Supabase CLI / project" for the human to run later.

## Review findings (address before DONE)

A reviewer found that `policy_select_device` in `0002_rls.sql` causes **infinite recursion**,
breaking `SELECT` on the `policy` table for **everyone** (parents included, not just devices) —
verified live: `select * from public.policy` as an authenticated parent errors with
`infinite recursion detected in policy for relation "policy"`. The bug: the policy's USING
clause embeds a raw correlated subquery against `public.policy` itself (the max-version lookup)
without wrapping it in a `security definer` function, unlike every other cross-table lookup in
the file (`current_parent_family_ids`, `current_parent_child_ids`, `current_device_child_id`),
which all correctly avoid recursive RLS evaluation via that pattern.

**Fix required (verified working by the reviewer against the live local instance):**
```sql
create or replace function public.policy_max_version(p_child_id uuid)
returns integer language sql stable security definer set search_path = public
as $$ select max(version) from public.policy where child_id = p_child_id; $$;

create policy policy_select_device on public.policy
  for select to authenticated
  using (
    child_id = public.current_device_child_id()
    and version = public.policy_max_version(policy.child_id)
  );
```
Apply this fix to the migration file itself (not just the live container — the reviewer patched
the running container only to verify, then reverted via `supabase db reset` to leave the repo's
migration files untouched, so the fix still needs to land in your SQL file). Re-verify with
`supabase db reset` + `scripts/smoke.ts`, AND add a live check (or a note in the report of a
manual one) that a parent JWT can actually `SELECT` from `policy` for their own child without
the recursion error — this is the regression test that would have caught the bug, add it as a
lightweight addition to `scripts/smoke.ts` (assert a policy row round-trips for a parent-scoped
client, not just the service-role client) since a full pgTAP suite is still an acceptable
follow-up per the ticket's original allowance.
