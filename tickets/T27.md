# T27 — iOS native: FamilyControls screen time integration

## Context
Spec §2.2/§8: `FamilyControls`/`ManagedSettings`/`DeviceActivity` (screen time API — "the only
sanctioned mechanism" per Apple). Spec §8: "Apple: FamilyControls entitlement application
required (weeks of lead time — start early)."

**Human gate, explicit:** actually obtaining the FamilyControls entitlement requires the
human's own Apple Developer Program account (paid, $99/yr) and submitting Apple's entitlement
request form with a business justification — this is not something an executor can do (no
account exists, and it's an identity/business decision, not a coding task). This ticket writes
the real Swift integration code against the public `FamilyControls`/`ManagedSettings`/
`DeviceActivity` API surface (which can be referenced/typechecked without the entitlement — the
entitlement only gates *runtime* authorization, not compilation) and prepares everything so
that the moment a human has the entitlement + provisioning profile, it's a matter of flipping
on the capability in Xcode, not writing new code.

Same `swiftc -typecheck` verification approach as T26.

Reuses `SchedulePolicy`/`ScreenTimePolicy`/`AppRulePolicy` (T02) — same shapes Android T22-T24
enforce, translated to Apple's `ManagedSettings` primitives (`ShieldConfiguration`,
`ApplicationTokens`, `DeviceActivitySchedule`).

## Requirements
In `app/ios/Guardian/ScreenTime/`:

1. `ScreenTimeAuthorization.swift` — wraps `AuthorizationCenter.shared.requestAuthorization` for
   `.individual` (or `.child` if using Family Sharing-based parental setup — document which
   mode is chosen and why: `.child` matches this product's model of "child's own device" more
   closely than a Family Sharing parent-managed mode; note this as a design decision the human
   should confirm once they can actually test against the real entitlement).
2. `ManagedSettingsController.swift` — translates T02's `AppRulePolicy.blockedApps` +
   `ContentFilterPolicy` categories into `ManagedSettingsStore` shielding
   (`store.shield.applications`, `store.shield.webDomains`), and `ScreenTimePolicy`/
   `SchedulePolicy` into `DeviceActivitySchedule` + `DeviceActivityCenter` monitoring, with a
   `DeviceActivityMonitor` extension target reporting usage events back through the RN bridge
   (feeds the same `DeviceEvent`/`app_usage` shape T24 produces on Android — restate: `{ id,
   deviceId, childId, type: 'app_usage', payload, occurredAt }`).
3. `ScreenTimeModule.swift` — RN bridge exposing `requestAuthorization()`, `applyPolicy(policy)`,
   `getAuthorizationStatus()` to JS.
4. Add a **prominent code comment block** at the top of `ScreenTimeAuthorization.swift` stating
   exactly: "Requires the `com.apple.developer.family-controls` entitlement, an Apple Developer
   Program membership, and (for now) a TestFlight/development provisioning profile with the
   entitlement approved by Apple. Without it, `requestAuthorization` will throw at runtime even
   though this file compiles."
5. Run and paste `swiftc -typecheck` output per new file, same as T26.

## Out of scope
- Actually submitting Apple's entitlement application form — that's T28 (compliance artifacts;
  drafts the application content) plus a real human action outside any ticket (submitting via
  Apple's developer portal with their account).
- Full signed build/run — blocked on the entitlement, by definition.
