# T04 — Presence/attention signal-ladder policy logic

## Context
Differentiator 3 (spec §6). This ticket is the **policy/decision layer only** — pure logic
that decides, given raw signal inputs, whether a trigger fires and what should happen. The
actual sensors (touch/scroll listeners, accelerometer, CameraX+MLKit face detection) are native
and belong to later Android tickets (T25); this ticket must be fully unit-testable without any
native code, by accepting signal inputs as plain data.

Restated rules from spec §6:
- **Level 0** (always on, no sensors): no touch/scroll/key input for N minutes while a "watched"
  app is foreground → dim → warning → lock/pause. Distinguish "watching" video (expected
  no-touch) via an `audioFocusActive` input plus periodic "Still watching?" prompts (30s to
  respond) — if the prompt times out with no response, treat as abandoned.
- **Level 1**: device motion — accelerometer/gyroscope stillness for N minutes while a game is
  foreground implies abandonment.
- **Level 2** (Android only): two consecutive "no face" boolean samples → pause timer + lock.
- Each level is independently toggleable (`PresencePolicy.level0Enabled` etc. from T02), each
  with its own `thresholdMinutes` entry.
- On trigger: apply `PresencePolicy.onTrigger` (`pauseTimer` | `lockScreen` | `both`).
- **Refund**: abandoned minutes are refunded to the child's daily bucket (Phase-0/spec bonus
  fairness feature) — call `BucketEngine.refundMinutes` (T03) with the minutes elapsed since
  the *threshold* was crossed (i.e. don't refund the attentive time before the trigger, only
  the idle tail).
- **Notification**: Phase-0 decision — parent is notified via real-time push on **every**
  trigger (not digest-only). This ticket only needs to emit a typed event/intent
  (`{ type: 'presence_trigger', childId, deviceId, level, minutesRefunded, occurredAt }`) that
  a later backend ticket (T09) turns into an actual push; do not implement push delivery here.

## Requirements
In `packages/domain/src/presence/`:

1. `types.ts` — `PresenceSignalSample` (`level0Idle: boolean` [derived upstream from
   input-inactivity duration crossing threshold], `stillPromptTimedOut: boolean`,
   `level1Still: boolean`, `level2FaceSamples: boolean[]` [rolling window, most recent last],
   `foregroundAppCategory: string`, `now: string`).
2. `evaluator.ts` — `evaluatePresence(policy: PresencePolicy, sample: PresenceSignalSample,
   sessionStartedAt: string): PresenceDecision` where `PresenceDecision` is
   `{ triggered: boolean; level?: 0|1|2; action?: 'pauseTimer'|'lockScreen'|'both';
   minutesToRefund: number; event?: DeviceEvent }` (reuse `DeviceEvent`/`EventType` from T02 —
   add `'presence_trigger'` if not already in the `EventType` union from T02; if T02 already
   included it, just reuse it).
   - Only evaluate levels that are enabled in `policy`.
   - Level 2 requires **two consecutive** `false` entries at the end of `level2FaceSamples`.
   - If multiple levels trigger simultaneously, use the lowest-numbered triggered level for the
     event but apply the union of configured actions (still just resolves to `policy.onTrigger`
     since that's a single global setting, not per-level).
3. `__tests__/evaluator.test.ts` — cover: each level triggering independently when the others
   are disabled; level 2 requiring two consecutive false samples (one false alone does not
   trigger); disabled level never triggers even if its raw signal says idle; refund minutes
   calculation only counts idle tail, not full session; "Still watching?" prompt timeout counts
   as abandonment for Level 0.

## Review findings (address before DONE)

A reviewer found that Level 0's trigger condition (`level0Idle && stillPromptTimedOut`) wrongly
requires the "Still watching?" prompt timeout as a mandatory gate for *every* Level-0 trigger.
Per this ticket's own Context: the base rule is "no touch/scroll/key input for N minutes ... →
dim → warning → lock/pause" for **any** watched app — the prompt exists only to stop that base
rule from false-triggering during **legitimate video watching** (where no-touch is expected).
As implemented, a game left idle past the threshold with no video/audio playing can **never**
trigger Level 0, since `stillPromptTimedOut` only ever becomes true when a prompt was actually
shown (i.e., only for video-type content) — this breaks the spec's lead scenario. The
`foregroundAppCategory` field (already in `PresenceSignalSample`, already populated in every
test fixture) was never read anywhere in `evaluator.ts` — it's the field that should gate when
the prompt requirement applies.

**Fix required:** Level 0 should trigger on `level0Idle` alone for non-video foreground
categories; only for video-type content should the trigger additionally require
`stillPromptTimedOut` (idle time alone is expected/legitimate while watching, so it must not
trigger until the prompt is shown and times out). Since the canonical content-category id list
doesn't exist yet in this codebase (it's built later, in T15), define a small local constant in
`presence/evaluator.ts` for now — e.g. `const VIDEO_LIKE_CATEGORIES = new
Set(['video_streaming', 'video', 'youtube'])` — with a comment flagging that **T15 must
reconcile this against its final category id list** (add a `RISK:` note to this effect in your
report so the orchestrator can patch T15 or a later ticket to align them). Update
`evaluator.ts`'s Level 0 branch to: `sample.level0Idle && (!VIDEO_LIKE_CATEGORIES.has(
sample.foregroundAppCategory) || sample.stillPromptTimedOut)`. Fix the test that currently
locks in the wrong behavior (`'idle alone without the prompt timing out does not trigger'`) to
instead test this correctly for a **video** category, and add a new test asserting idle-alone
**does** trigger Level 0 for a non-video category (e.g. `'games'`) with no prompt involved.
