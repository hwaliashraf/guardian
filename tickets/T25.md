# T25 — Android native: motion + camera presence detection, on-device NSFW classifier

## Context
Spec §6, Levels 1-2: "Device motion... accelerometer/gyroscope stillness. Periodic camera
presence check (Android only)... foreground service samples the front camera for ~1 second
every N minutes and runs on-device face detection (ML Kit)... No images ever leave the device;
no images are stored; no face recognition, only detection." **Privacy guardrails are
non-negotiable per spec §6** — this ticket must implement them literally: boolean-only result,
no persistence of frames, no upload, explicit opt-in gating, persistent notification while
active.

Spec §4, Layer 2 (reduced scope per Phase-0/LEDGER.md decision: no bundled browser this pass —
build the classifier as a standalone callable module, not wired into a full browser, since
that product surface doesn't exist in this build): "on-device NSFW classifier (TFLite, <50
ms/image)."

Same environment caveat as T22-T24 (no Java — written for real, unverified here). Additionally,
a real TFLite `.tflite` NSFW model file is a **binary asset this ticket cannot download/train**
in this environment — do not fabricate a fake/placeholder model file. Instead: wire the
classifier module against the TFLite Interpreter API with a clearly documented expected model
filename/path (`app/android/app/src/main/assets/nsfw_classifier.tflite`) and add the exact
sourcing step to `SETUP.md` (a human obtains an existing open NSFW TFLite model — e.g. one of
the several open-source "NSFW image classifier" TFLite conversions — and drops it at that
path; name at least one concrete open-source project the spec itself points at: "open NSFW
models" per spec §2.2).

Feeds T04's `evaluatePresence`: this module's output must be shaped to fill
`PresenceSignalSample.level1Still` and `.level2FaceSamples` exactly as T04 (and T23's bridge
event, if that's where partial samples are merged — check T23's report for its `RISK:` note on
this and follow whatever merge point it settled on, or flag your own `RISK:` if T23 left it
ambiguous).

## Requirements
In `app/android/app/src/main/kotlin/com/guardian/presence/` and `.../nsfw/`:

1. `MotionMonitor.kt` — accelerometer/gyroscope listener; stillness-for-N-minutes detection
   while a game category is foreground (consumes foreground-category signal from T23/T24's
   bridge), emits the `level1Still` boolean into the shared presence-sample bridge.
2. `CameraPresenceService.kt` — foreground service (`foregroundServiceType="camera"` per spec
   §8's Play Store requirement), CameraX front-camera sample every N minutes (N from
   `PresencePolicy.thresholdMinutes.level2`), ML Kit `FaceDetector` on the single frame,
   discards the frame immediately after (no `Bitmap` retained past the detection call — write
   this so it's structurally impossible to accidentally persist, e.g. process the frame inside
   a `try`/`finally` that nulls the reference), appends the boolean result to a small rolling
   window feeding `level2FaceSamples`, requires and displays a **persistent notification**
   while active (non-dismissible while the service runs), and only starts if the policy's
   `level2Enabled` is true AND a one-time on-device "camera opt-in" setup flag has been set
   (add this flag to local device storage — the child-device setup flow that sets it is a
   small addition inside T21's app if not already covered; if T21 doesn't have a camera-opt-in
   step, flag this as a `RISK:` note for the orchestrator rather than silently adding a whole
   new screen here — this ticket's job is the native module, not new RN screens).
3. `NsfwClassifier.kt` — TFLite `Interpreter` wrapper, `classify(bitmap): Float` (NSFW score
   0-1) targeting <50ms/image per spec KPI (document the model's expected input tensor
   shape/normalization as constants, matching whatever open NSFW TFLite conversion the human
   will source per `SETUP.md`). Expose via `NsfwModule.kt` RN bridge:
   `classifyImageUri(uri): Promise<{ nsfwScore: number; blocked: boolean }>` — since there's no
   bundled browser, document in a code comment that the integration point for this pass is a
   share-intent/manual "scan this image" action (or a future browser-extension hook), not
   automatic in-page scanning.
4. `PresenceModule.kt` — RN bridge wiring `MotionMonitor` + `CameraPresenceService` into the
   shared presence-sample bridge event that ultimately reaches T21's `useLocalBucketEngine`.
5. Privacy guardrail checklist (spec §6, restate as literal code-level facts to verify in the
   report, one line each): boolean-only result persisted/logged (never the frame); no network
   call ever made with camera data; persistent notification shown while `CameraPresenceService`
   runs; feature gated off unless `level2Enabled` **and** opt-in flag set.
