# T26 — iOS native: DNS profile & Safari Content Blocker

## Context
Spec §2.1: iOS is a "reduced companion set — Web filtering via Safari content blocker + DNS
profile... no background camera, no system-wide ad inspection." Spec §2.2:
`NEDNSSettingsManager` (DNS filtering), Safari Content Blocker extension.

**Environment reality, better than Android's:** Xcode 15.4 IS installed. There's no Apple
Developer account/entitlement and no physical iOS device, so a full signed app build/run
cannot happen — but plain Swift **type-checking against the iOS SDK does not require an
entitlement or a device**, only Xcode's bundled SDKs. Attempt this as real, if partial,
verification: `xcrun swiftc -sdk $(xcrun --sdk iphonesimulator --show-sdk-path) -target
arm64-apple-ios17.0-simulator -typecheck <file>.swift` for each new Swift file (adjust target
per whatever SDK version Xcode 15.4 ships). If a file doesn't typecheck standalone because it's
part of a larger module (likely, given cross-file references), that's fine — state which files
typechecked cleanly standalone and which need the full Xcode project to check, and note the
`xcodebuild -scheme ... build` command as the follow-up step in `SETUP.md` under "Xcode /
CocoaPods."

Reuses `ContentFilterPolicy` (T02/T15) — same policy shape the Android VPN (T22) reads.

## Requirements
In `app/ios/Guardian/DNSFilter/` (create the directory tree even if `app/ios/` is a T11
fallback placeholder — same caveat as T22's Android note):

1. `DNSFilterManager.swift` — wraps `NEDNSSettingsManager` to install/remove a custom DNS
   settings profile pointing at a DNS resolver enforcing the same category/domain blocklist
   policy as T22's Android `BlocklistLoader` (document that iOS relies on a **server-side or
   locally-run DoH resolver** rather than a local packet-level TUN filter, since
   `NEDNSSettingsManager` only lets you specify a DNS server, not inspect packets like Android's
   `VpnService` — this is an intentional, spec-acknowledged platform capability gap, not a bug).
2. `GuardianContentBlocker/` — a new Safari Content Blocker **extension target** structure
   (`ContentBlockerRequestHandler.swift`, `Info.plist`, extension entitlements file) generating
   `contentBlockerRules.json` from the same `ContentFilterPolicy` (a build-time or app-side
   generation script, `Scripts/generateContentBlockerRules.ts` in `packages/domain` or `app/`,
   pure/testable — pick `packages/domain/src/ios/contentBlockerRules.ts` for testability,
   exporting `buildContentBlockerRules(policy: ContentFilterPolicy): object[]` per Apple's
   documented content-blocker JSON rule schema (block-list-of-URLs-by-domain style rules),
   with Jest tests).
3. `DNSFilterModule.swift` (+ Objective-C bridging header if the RN iOS bridge needs one) —
   exposes `installProfile()`, `removeProfile()`, `isActive()` to JS via RN's native module
   bridge (`RCT_EXPORT_MODULE`).
4. Run the `swiftc -typecheck` check described above on every new `.swift` file and paste the
   actual output (success or the specific error) for each — do not claim verification without
   pasting real command output.

## Out of scope
- Full signed app build (no entitlement/device/provisioning profile — see T27 for the entitlement
  application process itself, which is a compliance/human-gated ticket, not this one).
- Android-parity ad-network/text-heuristic layers — spec explicitly scopes these out for iOS.
