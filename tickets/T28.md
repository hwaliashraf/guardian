# T28 — Compliance artifacts

## Context
Spec §8, restated: COPPA/GDPR-K verified parental consent (implemented in T10) + data
minimization + child data deletion on account close (implemented in T10 via cascade delete);
Google Play must declare Accessibility + VpnService + Device Admin usage with "a prominent
disclosure screen and policy justification," camera use needs foreground-service type
`camera` + clear disclosure (T22/T23/T24/T25 left `// see T28` markers for this); Apple
FamilyControls entitlement application (T27 is code-ready, application submission itself is a
**human action outside this pipeline** — this ticket only drafts the application content).
Spec §6 privacy guardrails: camera-level presence detection "documented plainly in the privacy
policy."

**Human gate, explicit:** this ticket produces *documents/drafts* for the human to review,
adapt to their legal entity, and actually submit/publish — it does not and cannot constitute
legal advice or a submitted/binding filing. State this plainly at the top of every document
produced.

## Requirements
Create `docs/compliance/` at the project root:

1. `privacy-policy-draft.md` — plain-language privacy policy draft covering: what data is
   collected (family/child/device registry, policy settings, event logs, location if enabled),
   what is explicitly NOT collected/stored (camera frames — boolean-only per T25; images from
   NSFW scanning are not persisted; no message-content monitoring), COPPA/GDPR-K consent
   mechanism (T10's `consentAccepted` flow), data deletion on account close (T10's cascade
   delete), and a dedicated section transparently explaining the camera-based presence
   detection feature (spec §6's "documented plainly... likely a differentiating trust point").
2. `play-store-disclosure.md` — the in-app "prominent disclosure screen" copy required before
   requesting Accessibility/VpnService/Device Admin/Camera permissions, matching Play's
   accessibility-usage and permitted-use policy for parental-control apps, plus the exact
   policy-justification text to paste into the Play Console's permissions declaration form.
3. `apple-entitlement-application-draft.md` — the business-justification text Apple's
   FamilyControls entitlement request form asks for (what the app does, why the entitlement is
   needed, how it complies with Apple's parental-control app guidelines), ready for the human
   to paste into their own Apple Developer account's request form. Include a checklist of what
   the human still needs to do themselves: (a) enroll in the Apple Developer Program, (b)
   submit this entitlement request, (c) wait for approval (spec: "weeks of lead time"), (d)
   generate a provisioning profile once approved, (e) flip on the FamilyControls capability in
   Xcode for the `app/ios` target (T27's code is otherwise ready).
4. `coppa-gdprk-checklist.md` — a short checklist mapping each compliance requirement to the
   ticket/file that implements it (consent → T10, deletion → T10, data minimization → T25's
   camera guardrails + this doc, disclosure → item 2 above) so a human reviewer can audit
   coverage without re-reading every ticket.
5. Wire the actual disclosure screen copy from item 2 into a real RN screen,
   `app/src/child/onboarding/PermissionsDisclosureScreen.tsx`, shown before any of the
   Android-permission-requesting flows — this is the one piece of this ticket that's real
   product code, not just a document; add a test asserting it renders every permission's
   disclosure text.

## Out of scope
- Actually submitting anything to Apple or Google — human action, outside this pipeline.
- Legal review/sign-off — flagged as a human_gate for exactly this reason.
