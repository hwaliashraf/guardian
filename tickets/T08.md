# T08 — Policy sync + push dispatch edge functions

## Context
Spec §7: "Policy push latency target: <10 s from parent tap to child device (FCM
high-priority)." Spec §3.1: "Instant pause: parent locks all family devices with one tap."
This ticket implements the write-path: a parent updates a `Policy`, the backend persists a new
version and dispatches a push to every device belonging to that child (or, for instant pause,
every device in the family) so the child device can pull the fresh policy immediately.

No FCM/APNs project credentials exist in this environment (no Firebase account per
LEDGER.md) — implement the dispatch as a real, swappable interface
(`PushDispatcher.send(deviceToken, payload)`) with a concrete `LoggingPushDispatcher`
(writes to a `push_log` table instead of a real network call) wired in by default, and a
`FcmPushDispatcher` implementation written for real against the FCM HTTP v1 API shape but
gated behind an env var (`FCM_SERVICE_ACCOUNT_JSON`) that won't be set here — document in
`SETUP.md` under a new "FCM / push credentials" section exactly what a human needs to obtain
(Firebase project, service account JSON) and where to put it to switch dispatchers.

Reuses `Policy` type from T02 and `hasFeature`/`assertFeature` from T06 (restate: policy writes
that touch premium-gated sub-policies — e.g. `presence` fields being enabled, or `buckets`
being configured — must call `assertFeature(tier, 'presence_detection' | 'usage_buckets')`
first and reject with 403 + `FeatureGatedError` info if the family's tier doesn't allow it).

## Requirements
In `packages/backend/supabase/functions/`:

1. `policy-sync/index.ts` (Supabase Edge Function, Deno runtime):
   - `PUT /policy-sync/:childId` — body is a partial `Policy` update. Loads the family's
     `Subscription.tier`, calls `assertFeature` for every gated sub-policy touched (buckets →
     `usage_buckets`, presence → `presence_detection`, appRules per-app limits →
     `per_app_limits`, contentFilter VPN-shield-specific fields → `vpn_shield`), increments
     `Policy.version`, persists, then dispatches push to all of that child's `Device` rows.
     Target: function body must complete (DB write) in well under the 10s budget on local dev —
     record actual latency in the report if `supabase start` is up (from T07); if not, this is
     unverified for the same Docker reason as T07 and must be stated as such.
   - `POST /policy-sync/instant-pause` — body `{ familyId }`; sets `instantPause: true` +
     bumps `version` on every child's active `Policy` in the family, dispatches push to every
     device in the family.
2. `push/dispatcher.ts` — the `PushDispatcher` interface + `LoggingPushDispatcher` +
   `FcmPushDispatcher` as described in Context. `push_log` table added via a new migration
   `packages/backend/supabase/migrations/0003_push_log.sql` (`device_id, payload jsonb,
   dispatched_at, dispatcher('logging'|'fcm')`).
3. Unit tests (Deno test or, if simpler, extract the pure decision logic — "which devices to
   notify," "which features are gated" — into a plain TS module under
   `packages/backend/src/policySync.ts` importable by both the edge function and
   `packages/backend/src/__tests__/policySync.test.ts` run via the root Jest config; keep the
   edge function itself a thin HTTP wrapper around this pure module so it's testable without a
   Deno-specific test runner). Cover: gated feature rejected with correct tier info;
   ungated update succeeds and version increments; instant-pause touches every family device;
   push dispatched exactly once per device.

## Review findings (address before DONE)

A reviewer found that adding `allowImportingTsExtensions: true` to the root
`tsconfig.base.json` (done to support `.ts`-extensioned relative imports in
`packages/domain/src/tiers/{gate,features}.ts`, needed for Deno compatibility) broke
`packages/domain`'s own `build` script: `npm run build -w packages/domain` now fails with
`TS5096: Option 'allowImportingTsExtensions' can only be used when one of 'noEmit',
'emitDeclarationOnly', or 'rewriteRelativeImportExtensions' is set` — because that build runs
`tsc -p tsconfig.json` (an emitting build, no `--noEmit`) and inherits the option from the base
config. Verified by the reviewer via git-stash A/B testing that this regression is introduced
by this ticket's diff, not pre-existing, and that `npm run build -w packages/domain` is a
verification gate re-checked in every prior ticket that touched domain files (T02, and others).

**Fix required (verified working by the reviewer):** add `"rewriteRelativeImportExtensions":
true` to `packages/domain/tsconfig.json`'s `compilerOptions` (supported by this repo's
TypeScript 6.0.3) — this makes `npm run build -w packages/domain` succeed again and correctly
emits `.js`-rewritten imports (e.g. `dist/tiers/gate.js` imports `./features.js`, not
`./features.ts`). Apply this fix, then re-verify `npm run build -w packages/domain` passes
(paste the output) alongside re-confirming `npm test -w packages/domain` (97/97) and
`npm test -w packages/backend` (20/20) are still green.
