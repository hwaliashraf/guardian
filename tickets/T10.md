# T10 — Auth, family/device registry & verified-parental-consent flow

## Context
Spec §8 (Compliance): "COPPA / GDPR-K: verified parental consent flow at signup; data
minimization; child data deletion on account close." Spec architecture (§7): parent app and
child app both authenticate against the same backend; child devices pair to a family via some
registration flow (spec doesn't specify the mechanic — this ticket must design a concrete
pairing-code flow since none is given, and flag it as a `RISK:` design decision in the report
for human review, not silently assumed).

Design decision this ticket must implement (documented, not asked, since it's an implementation
detail not a product/scope decision): **short-lived pairing code**. Parent generates a 6-digit
code from the parent app scoped to one `Child` record; child device app enters the code within
a TTL (10 minutes) to register itself as a `Device` and receive a scoped device credential.

## Requirements
In `packages/backend/`:

1. Use **Supabase Auth** (email/password + email confirmation) for parent accounts — this is
   part of Supabase itself, not a new vendor dependency.
2. `supabase/migrations/0005_pairing.sql` — `pairing_code { code, child_id, expires_at,
   consumed_at }`.
3. Edge function `auth-flows/index.ts`:
   - `POST /auth-flows/signup` — creates the parent's Supabase Auth user, then a `Family` +
     `Parent` row linked to `auth.uid()`. Include a `parentalConsentAcceptedAt` timestamp field
     (add via migration `0005_pairing.sql` alongside pairing table, on the `Family` or `Parent`
     row — pick `Parent`) that must be set (request body requires an explicit
     `consentAccepted: true` boolean) before the signup completes — this is the "verified
     parental consent flow at signup" the spec requires; reject signup with a clear error if
     `consentAccepted` is not `true`.
   - `POST /auth-flows/children` — parent creates a `Child` record under their family.
   - `POST /auth-flows/pairing-code` — parent requests a code for a given `childId`; returns
     the 6-digit code + expiry.
   - `POST /auth-flows/pair-device` — child app submits `{ code, platform, deviceName }`;
     validates not expired/not consumed, creates the `Device` row, marks the code consumed,
     returns a device-scoped credential (a Supabase `service_role`-signed JWT with a custom
     `device_id` claim, consistent with the RLS assumption documented in T07 — reuse that
     exact claim shape, do not invent a different one).
   - `DELETE /auth-flows/family` — account close: deletes the `Family` row; rely on the
     `ON DELETE CASCADE` foreign keys from T07's migration to cascade-delete every child,
     device, policy, event, and request under it (data-minimization/deletion requirement) —
     verify this cascade actually works if a local Supabase instance is available (T07's
     Docker status), otherwise document as unverified.
4. Pure/testable module `src/pairing.ts` (code generation + expiry/consumption checks) with
   `src/__tests__/pairing.test.ts`: code expires after TTL, one-time use, wrong code rejected.

## Out of scope
- Any actual identity verification beyond email confirmation (e.g. credit-card-based age
  verification some COPPA approaches use) — out of scope for v1 per spec's brevity on this
  point; flag as noticed-not-touched.
- Parent app UI for these flows — T11.
